## What this system is

This is a FastAPI-based semantic ad retrieval service. A client sends a natural language query with optional user context — age, gender, location, interests, device — and the system returns up to 1,000 ranked campaign results, an ad eligibility score, extracted content categories, and a detailed metadata payload. The whole thing runs in a single HTTP round-trip targeting p95 < 100ms. Saved test-suite snapshots show p50 at ~9ms and p95 at ~31ms, with plenty of headroom.

The design makes two commitments that shape everything else: safety is non-negotiable and must fail closed, and the system must be debuggable at the request level without needing a profiler or a second query.

---

## How the pipeline works

Every request passes through six sequential phases, with phases 3 and 4 running in parallel to minimize wall time.

**Phase 1 — Blocklist check.** The query is matched against a two-tier blocklist: a built-in regex layer of known unsafe patterns, optionally extended by a deploy-time additions file. A hard match exits immediately with `ad_eligibility=0.0` and no campaigns. This phase costs microseconds and runs before any model inference.

**Phase 2 — Embedding.** The query is embedded once using `all-MiniLM-L6-v2` via an ONNX runtime backend. The resulting 384-dimensional vector is shared across all downstream phases. Embedding costs roughly 8–20ms and was chosen over larger models (MPNet, E5) that would double FAISS index memory and inference time, and over API-based embeddings (OpenAI) that add 30–80ms of network latency — incompatible with the 100ms budget.

**Phase 3 — Parallel stage.** Three tasks run concurrently over the query vector:

- *Eligibility scoring*: a three-layer pipeline — soft-cap blocklist patterns, a lightweight joblib TF-IDF + logistic regression classifier trained on ad-appropriateness signals, and a k-means cluster centroid matcher covering eight sensitive topic areas (self-harm, grief, medical crisis, financial distress, etc.). Each layer is independent; a match on any one layer can hard-gate the query. The continuous output is a `[0, 1]` score shaped by `(1 - sensitivity_penalty) × commercial_boost`, with commercial boost neutralized when sensitivity exceeds 0.70. The model fails closed — exceptions set `insensitive_prob=1.0` and gate the query.
- *Category extraction*: the query vector is searched against a FAISS index of ~975 representative user queries tagged with one of 133 categories across 20 verticals. Matching query-to-query is more accurate than matching against taxonomy description strings because users don't search in taxonomy language. Context boosts, coherence-ratio filtering, and a fallback floor handle sparse and ambiguous signals.
- *FAISS retrieval*: `IndexFlatIP` exact inner-product search over 10,783 L2-normalized campaign embeddings returns up to 1,000 candidate IDs and cosine scores. Exact search was chosen over approximate ANN (HNSW, IVF) because at this corpus size (~16MB of float32 data) the index fits in L2/L3 cache and exact search costs ~1–3ms — approximate search would lose recall with no latency benefit. No external vector database is used; the network round-trip alone would consume the parallel-stage budget.

**Phase 4 — Query parsing.** Lexical parsing extracts brand terms, price range intent, attribute signals (sustainable, vegan, cruelty-free, etc.), negative terms, and user location from the raw query string. This feeds the hard eligibility filters in phase 5.

**Phase 5 — Campaign eligibility filtering.** Each candidate is evaluated against binary targeting constraints: geo include/exclude, age range, gender, price floor/ceiling, and negative keyword matching. These are deterministic hard filters — a campaign either can be served or cannot. The filter result reports per-filter drop counts, which surface directly in the response metadata.

**Phase 6 — Ranking.** The surviving candidates are scored by a componentized additive pipeline. Components cover FAISS base score, taxonomy alignment, category overlap, keyword signal, geo and demographic match, brand affinity, price range fit, and contradiction penalties. Each component returns a delta, which are summed and scaled by a coverage ratio so queries with more specified constraints don't uniformly punish campaigns that match most but not all of them. Weights live in `score_weights.yaml` and are tunable without code changes. Every top result's per-component breakdown is included in the response.

## Key design decisions

**Why the eligibility scorer is layered, not a single model.** Four alternative approaches were evaluated: a single k-means centroid scorer (MAE 0.195, unacceptable calibration for a safety gate), a two-pass orthogonal model (MAE improved to 0.146 but hard-block accuracy dropped to 78% — categorically unacceptable), `unitary/toxic-bert` inline (50–100ms per query, budget-fatal), and LLM-based classification (200–500ms per call, budget-fatal). The layered approach — blocklist + lightweight joblib model + cluster centroids — achieved 100% hard-block accuracy and MAE 0.087 with Spearman 0.905 at sub-millisecond inference cost. The layering also means each mechanism can be tuned or replaced independently.

**Why categories are suppressed on gated queries.** Returning extracted categories for a grief or crisis query — even when no campaigns are served — would surface signals like "baby food" or "life insurance," implying the system read the query in a commercial context. That's insensitive even if the outcome is a zero-result response. Categories are explicitly cleared after the eligibility gate before the response is assembled.

**Why the response is verbose.** The `metadata` payload includes per-phase timing, per-filter drop counts, per-component score breakdowns, the full eligibility detail, and the parser output. A missed ad is almost impossible to diagnose from the final ranking alone. Every metadata field was added to answer a specific diagnostic question without replaying the request.

**Why there is no query cache.** Natural language queries have near-zero exact-match hit rates in practice. A semantic cache (embed + similarity search against a Redis cache) requires infrastructure and introduces warm/cold latency distributions that are hard to reason about. Since p95 is already well below target on every query, the cache would add complexity without solving a real problem.

**Why ONNX over SentenceTransformer.** The ONNX backend eliminates PyTorch autograd graph overhead and Python-level dispatch. On CPU this reduces per-query embedding time by roughly 20–40%. Embedding is the largest single latency contributor, so this is the highest-leverage optimization available without changing the model.

## What I would do differently with more time

**1. A versioned evaluation framework.** This is the biggest gap. The system has all the ingredients — a diverse 56-query test suite, per-query output artifacts, per-component score breakdowns, safety test cases for hard-block and soft-gate scenarios — but they are not wired together into a reproducible regression harness. Right now, changing the eligibility threshold, updating the joblib model, or editing a score weight requires manually inspecting test outputs to check for regressions. The right fix is a CI-gated evaluation pipeline that tracks hard-block coverage, false-positive gating rate, nDCG@10, and p95 latency for every config change, with each run logged against a model hash and config snapshot. Without this, the system cannot safely evolve at speed.

**2. Labeled ground truth for ranking.** The ranking pipeline is interpretable and the score decompositions are detailed, but there is no judged relevance benchmark to validate that the componentized scores actually correspond to human-relevant ordering. Building even a modest set of query-campaign judgments (graded 0–3, ~200 queries × 50 candidates) would enable nDCG reporting and make weight tuning something you optimize toward rather than eyeball.


**3. Sigmoid normalization for `relevance_score`.** The output contract currently exposes a raw final score that can exceed 1.0, which conflicts with the documentation. The normalization experiment (`experiments/relevance-scoring/`) already shows the approach — z-score then sigmoid — but it wasn't adopted because it wasn't clear what the bounded signal would be used for. Resolving the `relevance_score` vs `internal_score` mismatch and settling on a single clean contract would reduce consumer confusion.

**4. Replace regex blocklist matching with Aho–Corasick.** The current blocklist uses compiled Python regex patterns iterated sequentially — fast enough at the current list size, but O(n × m) as the list grows. Aho–Corasick builds a finite automaton over all patterns at startup and scans the query in a single O(m) pass regardless of how many patterns exist. For a blocklist that grows over time (new sensitive topics, new phrasing variants, multilingual additions), this is the correct data structure: build cost is paid once at startup, match cost is constant per query, and the automaton can be swapped atomically on update without a code release.

**5. Shard the vector index by targeting parameters.** The current architecture runs FAISS search over the full 10k+ campaign corpus and then drops ineligible candidates in a post-retrieval filter step. At scale this wastes recall budget — if a query has `location=US-CA, gender=F, age=28`, a large fraction of the retrieved 1,000 candidates will be dropped immediately by hard geo, demographic, or budget filters before ranking even starts. The better approach is to pre-partition campaigns into shards by the targeting dimensions the query resolves at request time: geo region, gender, age band, and budget tier. At query time, only the shards that match the user context are searched, so every retrieved candidate is already eligible and the full recall budget is spent on semantically relevant results. This also opens the door to shard-level index refresh — updating a geo shard doesn't require rebuilding the full corpus index. The tradeoff is added build-time complexity and needing a fallback to the full index when context is sparse or absent, but for a system where context is frequently provided, the relevance gain is material.

**4. Load testing and a cold-start benchmark.** Current latency evidence comes from a single local run of 56 queries, not from sustained 
concurrency.

## Evaluation rubric

### Architecture & Design (25%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| System design | Clear separation of concerns, appropriate component boundaries | Each pipeline phase is a dedicated service module (`eligibility.py`, `categories.py`, `retrieval.py`, `ranking.py`, `campaign_eligibility.py`, `query_parser.py`). The scoring pipeline is further broken into independent component classes under `services/scoring/`. The blocklist uses a Strategy pattern — regex, ML, and composite strategies are interchangeable at config time with no code change. The embedding backend is swappable (ONNX vs SentenceTransformer) via `EMBEDDING_BACKEND` env var. All policy constants live in `eligibility_config.yaml`; all ranking weights in `score_weights.yaml` — tuning either requires zero code changes and only a service restart. |
| Latency optimization | Thoughtful approach to meeting the 100ms budget | The query is embedded once and the vector is shared across all downstream phases. Eligibility scoring, category extraction, and FAISS search run concurrently via `asyncio.gather` + `ThreadPoolExecutor` — wall time is the max of the three (~5ms), not the sum (~11ms). ONNX backend reduces per-embed time 20–40% over raw SentenceTransformer by eliminating PyTorch graph overhead. `IndexFlatIP` over 10k campaigns fits in L2/L3 cache and costs ~1–3ms exact. The blocklist hard-exits before any model inference. Startup preloads and warms all services so no request pays cold-start costs. Observed p50 ~9ms, p95 ~31ms against a 100ms target. |
| Scalability considerations | How would this handle 10× corpus? 100× QPS? | At 10× corpus (100k campaigns): swap `IndexFlatIP` for `IndexHNSWFlat` (M=32, ef=64) — no interface change required, only the artifact changes. At 100× corpus (1M): move to `IndexIVFPQ` accepting ~5–10% recall loss. For QPS scaling: the app is stateless with read-only artifact mounts, so horizontal scaling is straightforward — add replicas behind a load balancer. Each replica holds its own in-process FAISS index, avoiding shared-state contention. ONNX thread counts can be tuned per-replica via `OMP_NUM_THREADS`. The embedding model is the CPU bottleneck at scale; a GPU-backed inference service would be the natural next step. |
| Trade-off articulation | Document the trade-offs made and why | Every major architectural choice is documented with explicit alternatives evaluated and rejected: embedding model selection (3 models compared by cosine gap), FAISS type (exact vs approximate, external vs in-process), eligibility approach (4 alternatives benchmarked with MAE and hard-block accuracy), ranking approach (cross-encoder rejected on latency grounds, pure cosine rejected on targeting-constraint grounds), caching strategy (semantic cache rejected as complexity without benefit at current latency). See `docs/05-design-decisions/tradeoffs.md`. |

### Ad Eligibility Scoring (20%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| Safety filtering | Correctly identifies queries where ads should NOT be shown | Five-layer pipeline: regex/ML blocklist → joblib TF-IDF + LR classifier → k-means cluster centroid matcher over 8 sensitive topic areas (self-harm, grief, medical crisis, financial distress, addiction, violence, bereavement, abuse). Any layer firing can hard-block. The ML model and cluster centroids run in parallel and are OR-combined for maximum recall. The system fails closed — any model exception sets `insensitive_prob=1.0` and blocks. Hard-block accuracy is 100% on the saved 56-query test suite across self-harm, crisis, and bomb-making queries. |
| Score calibration | Scores are meaningful and consistent | Score is shaped by `(1 - sensitivity_penalty) × commercial_boost`, clamped to `[0, 1]`. This formula produces calibrated outputs: "best running shoes" → ~0.95 (high commercial, zero sensitivity), "I'm feeling stressed" → ~0.5 (low sensitivity but no commercial signal), "self-harm" → 0.0 (hard block). The layered approach achieved MAE 0.087 and Spearman 0.905 in the Option E experiment — the specific experiment result that determined the production architecture. Commercial boost is neutralized when `sensitivity_penalty > 0.70` to prevent commercial affinity from rescuing genuinely sensitive queries. |
| Efficiency | Scoring doesn't dominate the latency budget | Blocklist matching costs microseconds. Joblib model inference (TF-IDF + LR over a ~100KB artifact) costs sub-millisecond. Total eligibility scoring including cluster centroid matching is under 5ms. The entire eligibility phase runs in parallel with category extraction and FAISS search, so it contributes zero marginal latency to the wall-clock request time in the common case. |
| Edge case handling | Reasonable behavior on ambiguous or borderline queries | The continuous `[0, 1]` score allows nuanced treatment of borderline queries — they don't get hard-blocked, they get a reduced eligibility score that may or may not clear the `ELIGIBILITY_GATE=0.3` threshold. The gate was calibrated against the test suite: financial hardship and medical stress queries score 0.2–0.45 and are partially gated, which matches intended policy. Known false-positive patterns (e.g., "running shoes for my late father's marathon" touching grief vocabulary) are documented in `docs/05-design-decisions/safety-and-sensitivity.md`. |

### Category Extraction (20%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| Relevance | Extracted categories would actually match useful campaigns | Category extraction uses FAISS query-index mode: the query embedding is searched against ~975 representative user queries tagged with one of 133 categories across 20 verticals. Matching query-to-query produces more accurate results than matching against taxonomy description strings (e.g., "Athletic Footwear: shoes for sports activities") because users don't search in taxonomy language. Description-matrix mode is retained as an automatic fallback when the query-index artifacts are absent. |
| Granularity | Neither too broad nor too narrow | A coherence-ratio filter prunes secondary categories whose score falls significantly below the top match — preventing low-confidence noise categories from contaminating the output. A configurable `CATEGORY_THRESHOLD=0.40` sets the minimum confidence floor. A fallback floor ensures at least one category is returned for very short or ambiguous queries, preventing empty extraction on fragments. Top-5 categories are returned by default, covering genuine multi-intent queries without over-populating results. |
| Context utilization | User context influences extraction when appropriate | User interests from the context payload apply a score boost to matching categories. Gender context suppresses categories with a strong gender-mismatch signal. The full context dict is passed through from the request into the extractor, so any future context key can be used without an interface change. |
| Robustness | Handles varied query formats (questions, statements, fragments) | Embedding-based matching is format-agnostic — "best running shoes," "what are good running shoes for a marathon," and "running shoes marathon" all produce similar embeddings and retrieve the same categories. The fallback floor prevents empty results on minimal or unusual queries. The coherence gate prevents a single noisy high-scoring category from cascading into an implausible secondary category list. |

### Retrieval & Ranking (25%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| Ranking quality | Top results are meaningfully more relevant than lower results | Ranking uses a 9-component additive scoring pipeline on top of the FAISS base score: taxonomy alignment, category overlap (weighted by extraction confidence), keyword bucket matching, geo targeting match, demographic fit (age, gender, interests), brand affinity, price range alignment, and contradiction penalty for negative keywords. Components are weighted via `score_weights.yaml`. Coverage-ratio scaling ensures campaigns that satisfy most of a query's stated constraints rank above those that satisfy only one. Per-component score breakdowns are returned in `metadata.score_breakdown` for every top result, making ranking decisions auditable. |
| Search implementation | Efficient retrieval from 10k+ campaigns | `faiss.IndexFlatIP` exact inner-product search over 10,783 L2-normalized 384-dimensional campaign embeddings. At this corpus size, the full index is ~16MB and fits in L2/L3 cache — exact search costs ~1–3ms with no recall loss. All index artifacts are preloaded at startup into `app.state` so no request pays disk I/O. Hard campaign eligibility filters run after retrieval and are paired with a refill mechanism that pulls additional candidates if the initial 1,000 are heavily filtered. |
| Embedding/indexing strategy | Appropriate choice for latency and quality requirements | `all-MiniLM-L6-v2` was selected from a three-model comparison by average cosine gap between relevant and irrelevant query-document pairs: 0.6099 vs 0.6003 (`multi-qa`) vs 0.4837 (`msmarco`). `msmarco` scored worst because its asymmetric query-to-passage training poorly matches the symmetric short-form ad text. Campaign embedding text is generated as natural-language sentences from structured fields rather than keyword bags — this improves retrieval by reducing vocabulary mismatch. The v4 index additionally appends generated category and vertical query phrases to each campaign's embedding text to increase recall on category-level queries. |
| Score calibration | Relevance scores are interpretable and consistent | Two scores are exposed: `relevance_score` (raw final score, preserves ranking magnitude for downstream systems computing nDCG) and `internal_score` (clamped to `[0, 1]` by dividing by `q_max`, the theoretical maximum achievable for this query — suitable for UI display and A/B analytics). Component weights are kept in `[-1.0, 1.0]` to prevent any single signal from dominating the FAISS base similarity. A known contract mismatch where `relevance_score` can exceed 1.0 while docs imply clamped behavior is documented as a pending fix. |
