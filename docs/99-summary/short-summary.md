## Approach

This is a FastAPI-based semantic ad retrieval service: a client sends a natural language query with optional user context (age, gender, location, interests, device) and gets back up to 1,000 ranked campaigns, an ad eligibility score, extracted categories, and a detailed metadata payload — all in a single HTTP round-trip targeting p95 < 100ms. Saved test-suite snapshots show p50 ~9ms and p95 ~31ms. Two commitments shape every decision: safety must fail closed, and the system must be fully debuggable at the request level without a second query or a profiler.

The pipeline has six phases. A two-tier blocklist (regex + optional deploy-time additions) hard-exits in microseconds before any model runs. The query is then embedded once with `all-MiniLM-L6-v2` via ONNX — chosen over larger models that would blow the latency budget and over API embeddings that add 30–80ms of network overhead — and that vector is shared across three parallel tasks: eligibility scoring, category extraction, and FAISS retrieval. Eligibility uses a layered approach (blocklist → TF-IDF + LR joblib classifier → k-means cluster centroids across 8 sensitive topic areas) that achieved 100% hard-block accuracy and MAE 0.087 at sub-millisecond inference cost; four alternatives were benchmarked and rejected on calibration or latency grounds. Category extraction matches query-to-query against a FAISS index of ~975 representative queries across 133 categories and 20 verticals — more accurate than matching taxonomy descriptions because users don't search in taxonomy language. FAISS retrieval uses `IndexFlatIP` exact search over 10,783 campaigns; at ~16MB the index fits in L2/L3 cache and costs ~1–3ms, making approximate ANN a recall regression with no latency benefit. After the parallel stage, a lexical parser extracts brand terms, price intent, attributes, and geo signals to feed deterministic hard campaign filters (geo, age, gender, price, negative keywords). Surviving candidates are reranked by a 9-component additive scoring pipeline with weights in `score_weights.yaml` and coverage-ratio scaling — every component's delta is returned in the response for full auditability.

**Note on `relevance_score` values: scores may appear low on broad queries and that is expected behaviour. `relevance_score` is normalised by `q_max` — the theoretical maximum a campaign could score given this specific query and context. A query with no location, age, or brand context has a low `q_max`, so even a well-matched campaign scores modestly. Providing richer context (location, age, gender, interests) raises `q_max` and pushes scores higher because more targeting dimensions can be satisfied. The scores are intentionally query-relative, not absolute — a 0.4 on a bare query and a 0.4 on a fully-specified query are not the same thing.**

With more time, the top priority would be a versioned evaluation framework that ties every threshold, model, and weight change to reproducible safety and ranking metrics. The building blocks are there — 56 labeled test queries, per-query output artifacts, per-component score breakdowns — but they are not wired into a CI-gated regression harness. I would also collect judged query-campaign relevance labels to make weight tuning measurable (nDCG@10 rather than eyeballing), run load tests at multiple concurrency levels to establish a real p95 baseline beyond the current single-run snapshot, and resolve the `relevance_score` vs `internal_score` contract mismatch where the raw score can exceed 1.0 contrary to documented behavior.

## Evaluation rubric

### Architecture & Design (25%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| System design | Clear separation of concerns, appropriate component boundaries | Each pipeline phase is a dedicated service module (`eligibility.py`, `categories.py`, `retrieval.py`, `ranking.py`, `campaign_eligibility.py`, `query_parser.py`). The scoring pipeline is further broken into independent component classes under `services/scoring/`. The blocklist uses a Strategy pattern — regex, ML, and composite strategies are interchangeable at config time with no code change. The embedding backend is swappable (ONNX vs SentenceTransformer) via `EMBEDDING_BACKEND` env var. All policy constants live in `eligibility_config.yaml`; all ranking weights in `score_weights.yaml` — tuning either requires zero code changes and only a service restart. |
| Latency optimization | Thoughtful approach to meeting the 100ms budget | The query is embedded once and the vector is shared across all downstream phases. Eligibility scoring, category extraction, and FAISS search run concurrently via `asyncio.gather` + `ThreadPoolExecutor` — wall time is the max of the three (~5ms), not the sum (~11ms). ONNX backend reduces per-embed time 20–40% over raw SentenceTransformer by eliminating PyTorch graph overhead. `IndexFlatIP` over 10k campaigns fits in L2/L3 cache and costs ~1–3ms exact. The blocklist hard-exits before any model inference. Startup preloads and warms all services so no request pays cold-start costs. Observed p50 ~9ms, p95 ~31ms against a 100ms target. |
| Scalability considerations | How would this handle 10× corpus? 100× QPS? | At 10× corpus (100k campaigns): swap `IndexFlatIP` for `IndexHNSWFlat` (M=32, ef=64) — no interface change required, only the artifact changes. At 100× corpus (1M): move to `IndexIVFPQ` accepting ~5–10% recall loss. For QPS scaling: the app is stateless with read-only artifact mounts, so horizontal scaling is straightforward — add replicas behind a load balancer. Each replica holds its own in-process FAISS index, avoiding shared-state contention. ONNX thread counts can be tuned per-replica via `OMP_NUM_THREADS`. The embedding model is the CPU bottleneck at scale; a GPU-backed inference service would be the natural next step. |
| Trade-off articulation | Document the trade-offs made and why | Every major architectural choice is documented with explicit alternatives evaluated and rejected: embedding model selection (3 models compared by cosine gap), FAISS type (exact vs approximate, external vs in-process), eligibility approach (4 alternatives benchmarked with MAE and hard-block accuracy), ranking approach (cross-encoder rejected on latency grounds, pure cosine rejected on targeting-constraint grounds), caching strategy (semantic cache rejected as complexity without benefit at current latency). See `docs/05-design-decisions/tradeoffs.md`. |

### Ad Eligibility Scoring (20%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| Safety filtering | Correctly identifies queries where ads should NOT be shown | Five-layer pipeline: regex/ML blocklist → joblib TF-IDF + LR classifier → k-means cluster centroid matcher over 8 sensitive topic areas (self-harm, grief, medical crisis, financial distress, addiction, violence, bereavement, abuse). Any layer firing can hard-block. The ML model and cluster centroids run in parallel and are OR-combined for maximum recall. The system fails closed — any model exception sets `insensitive_prob=1.0` and blocks. Hard-block accuracy is 100% on the saved 56-query test suite across self-harm, crisis, and bomb-making queries. |
| Score calibration | Scores are meaningful and consistent | Score is shaped by `(1 - sensitivity_penalty) × commercial_boost`, clamped to `[0, 1]`. This formula produces calibrated outputs: "best running shoes" → ~0.95 (high commercial, zero sensitivity), "I'm feeling stressed" → ~0.5 (low sensitivity but no commercial signal), "self-harm" → 0.0 (hard block). The layered approach achieved MAE 0.087 and Spearman 0.905 in the Option E experiment — the specific experiment result that determined the production architecture. Commercial boost is neutralized when `sensitivity_penalty > 0.70` to prevent commercial affinity from rescuing genuinely sensitive queries. |
| Efficiency | Scoring doesn't dominate the latency budget | Blocklist matching costs microseconds. Joblib model inference (TF-IDF + LR over a ~100KB artifact) costs sub-millisecond. Total eligibility scoring including cluster centroid matching is under 5ms. The entire eligibility phase runs in parallel with category extraction and FAISS search, so it contributes zero marginal latency to the wall-clock request time in the common case. |
| Edge case handling | Reasonable behavior on ambiguous or borderline queries | The continuous `[0, 1]` score allows nuanced treatment of borderline queries — they don't get hard-blocked, they get a reduced eligibility score that may or may not clear the `ELIGIBILITY_GATE=0.3` threshold. The gate was calibrated against the test suite: financial hardship and medical stress queries score 0.2–0.45 and are partially gated, which matches intended policy. Known false-positive patterns (e.g., "running shoes for my late father's marathon" touching grief vocabulary) are documented in `docs/05-design-decisions/safety-and-sensitivity.md`. |

### Category Extraction (20%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| Relevance | Extracted categories would actually match useful campaigns | Category extraction uses FAISS query-index mode: the query embedding is searched against ~975 representative user queries tagged with one of 133 categories across 20 verticals. Matching query-to-query produces more accurate results than matching against taxonomy description strings (e.g., "Athletic Footwear: shoes for sports activities") because users don't search in taxonomy language. Description-matrix mode is retained as an automatic fallback when the query-index artifacts are absent. |
| Granularity | Neither too broad nor too narrow | A coherence-ratio filter prunes secondary categories whose score falls significantly below the top match — preventing low-confidence noise categories from contaminating the output. A configurable `CATEGORY_THRESHOLD=0.40` sets the minimum confidence floor. A fallback floor ensures at least one category is returned for very short or ambiguous queries, preventing empty extraction on fragments. Top-5 categories are returned by default, covering genuine multi-intent queries without over-populating results. |
| Context utilization | User context influences extraction when appropriate | User interests from the context payload apply a score boost to matching categories. Gender context suppresses categories with a strong gender-mismatch signal. The full context dict is passed through from the request into the extractor, so any future context key can be used without an interface change. |
| Robustness | Handles varied query formats (questions, statements, fragments) | Embedding-based matching is format-agnostic — "best running shoes," "what are good running shoes for a marathon," and "running shoes marathon" all produce similar embeddings and retrieve the same categories. The fallback floor prevents empty results on minimal or unusual queries. The coherence gate prevents a single noisy high-scoring category from cascading into an implausible secondary category list. |

### Retrieval & Ranking (25%)

| Criteria | What You're Looking For | What I Did |
|---|---|---|
| Ranking quality | Top results are meaningfully more relevant than lower results | Ranking uses a 9-component additive scoring pipeline on top of the FAISS base score: taxonomy alignment, category overlap (weighted by extraction confidence), keyword bucket matching, geo targeting match, demographic fit (age, gender, interests), brand affinity, price range alignment, and contradiction penalty for negative keywords. Components are weighted via `score_weights.yaml`. Coverage-ratio scaling ensures campaigns that satisfy most of a query's stated constraints rank above those that satisfy only one. Per-component score breakdowns are returned in `metadata.score_breakdown` for every top result, making ranking decisions auditable. |
| Search implementation | Efficient retrieval from 10k+ campaigns | `faiss.IndexFlatIP` exact inner-product search over 10,783 L2-normalized 384-dimensional campaign embeddings. At this corpus size, the full index is ~16MB and fits in L2/L3 cache — exact search costs ~1–3ms with no recall loss. All index artifacts are preloaded at startup into `app.state` so no request pays disk I/O. Hard campaign eligibility filters run after retrieval and are paired with a refill mechanism that pulls additional candidates if the initial 1,000 are heavily filtered. |
| Embedding/indexing strategy | Appropriate choice for latency and quality requirements | `all-MiniLM-L6-v2` was selected from a three-model comparison by average cosine gap between relevant and irrelevant query-document pairs: 0.6099 vs 0.6003 (`multi-qa`) vs 0.4837 (`msmarco`). `msmarco` scored worst because its asymmetric query-to-passage training poorly matches the symmetric short-form ad text. Campaign embedding text is generated as natural-language sentences from structured fields rather than keyword bags — this improves retrieval by reducing vocabulary mismatch. The v4 index additionally appends generated category and vertical query phrases to each campaign's embedding text to increase recall on category-level queries. |
| Score calibration | Relevance scores are interpretable and consistent | Two scores are exposed: `relevance_score` (raw final score, preserves ranking magnitude for downstream systems computing nDCG) and `internal_score` (clamped to `[0, 1]` by dividing by `q_max`, the theoretical maximum achievable for this query — suitable for UI display and A/B analytics). Component weights are kept in `[-1.0, 1.0]` to prevent any single signal from dominating the FAISS base similarity. A known contract mismatch where `relevance_score` can exceed 1.0 while docs imply clamped behavior is documented as a pending fix. |
